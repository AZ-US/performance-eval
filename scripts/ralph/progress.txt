## Codebase Patterns
- index.html is one giant Vue 3 Composition API file (`createApp({setup(){...}})`, ~6400 lines). No build step, no tests. All refs/functions used in the template must be added to the big `return {...}` object at the end of `setup()`.
- Cloud sync has three transports that must all carry the same fields: GET via JSONP (`fetchCloudJsonp`, script-tag with query params — used for `list`/verify), POST via `fetch(mode:'no-cors')` with a `sendBeacon` fallback and an iframe+form fallback (`submitCloudPayloadByForm`) — all three POST paths reuse the same serialized `body` string, so adding a field to that one `JSON.stringify({...})` call covers all three.
- Share links are built by 4 near-duplicate functions (`buildSharedUrl`, `buildScopedSharedUrl`, `buildEmployeeSharedUrl`, `buildOkrGroupSharedUrl`) that each independently set `cloud=` (and now `token=`) as URL params — remember to update all four when changing what a share link carries.
- The Google Apps Script backend (`google-apps-script-backend.js`) is a separate file that Amy manually pastes into her Apps Script project and redeploys — editing it in this repo does NOT update her live deployment. Any backend change must be called out explicitly as a manual step for Amy.

## [2026-09-10] - US-006
- Context: Amy reported a real recurring pain point outside the original PRD batch — "after finance (Agnes) finishes her review, I often can't see the result." Investigated the actual submit/sync code rather than guessing.
- Root cause found: `submitCurrentToCloud()` (index.html ~5195) fetches the existing cloud record by id (`findCloudRecordById`) before submitting, and if `evaluationInputQuality(existing) > evaluationInputQuality(record)` (a crude count of filled KPI/score/comment/OKR/bonus fields), it returned immediately WITHOUT ever calling `sendCloudPayload` — the submission never reached the network. The only feedback was a 2-second toast visible only to the person submitting (e.g. Agnes), with no signal to anyone else (e.g. Amy) that anything was blocked. Any time a new, genuine submission happens to have fewer filled fields than whatever was previously in the cloud for that employee+period (e.g. shorter/cleaner comments replacing old verbose ones, a field intentionally cleared), the real update is silently dropped.
- Implemented: replaced the silent `return` with a `confirm()` dialog (this codebase's established pattern for destructive/risky actions — see existing usages at lines ~5073, 5105, 5118, 5146, 6154, 6207, 6213) telling the submitter the cloud already has a record that looks more complete (with its saved time), and letting them choose to force-overwrite or cancel. Canceling preserves the original protective behavior (no overwrite); confirming proceeds through the normal `sendCloudPayload`/`verifyCloudSubmission` flow unchanged.
- Files changed: `index.html`.
- **Learnings for future iterations:**
  - To test cloud-sync code paths without a real Apps Script deployment: monkey-patch `document.head.appendChild` to intercept the `<script src="...&callback=...">` tag that `fetchCloudJsonp()` creates (match on a distinctive substring in the fake endpoint URL, extract `callback` from the query string, then call `window[callbackName](fakePayload)` directly instead of letting the script actually load) — this fully simulates the cloud GET/JSONP response. For the POST side, monkey-patch `window.fetch` and check `opts.method === 'POST'`. Also monkey-patch `window.confirm` to both capture the message shown and control the return value, to test both the "cancel" and "proceed" branches of a confirm-gated flow.
  - A secondary, NOT-yet-fixed related risk surfaced during this investigation: the whole per-employee-per-period record is one flat JSON blob, and the ordinary periodic sync path (`syncCloudRecords` → `mergeRecordList` → `normalizeRecordList` → `shouldReplaceRecord`) resolves conflicts purely by comparing client-reported `savedAt` timestamps (with only two narrow special-case guards for commission-plan quality and builtin-import records) — there is no field-level merge and no conflict warning. If two people edit the same employee+period record around the same time, whoever's save has the later timestamp wins wholesale, silently discarding the other's edits. This is a plausible contributing factor to the same "can't see finance's results" complaint and was flagged to Amy as a separate future story, not fixed here (out of scope for this specific bug report).
