## Codebase Patterns
- index.html is one giant Vue 3 Composition API file (`createApp({setup(){...}})`, ~6400 lines). No build step, no tests. All refs/functions used in the template must be added to the big `return {...}` object at the end of `setup()`.
- Cloud sync has three transports that must all carry the same fields: GET via JSONP (`fetchCloudJsonp`, script-tag with query params — used for `list`/verify), POST via `fetch(mode:'no-cors')` with a `sendBeacon` fallback and an iframe+form fallback (`submitCloudPayloadByForm`) — all three POST paths reuse the same serialized `body` string, so adding a field to that one `JSON.stringify({...})` call covers all three.
- Share links are built by 4 near-duplicate functions (`buildSharedUrl`, `buildScopedSharedUrl`, `buildEmployeeSharedUrl`, `buildOkrGroupSharedUrl`) that each independently set `cloud=` (and now `token=`) as URL params — remember to update all four when changing what a share link carries.
- The Google Apps Script backend (`google-apps-script-backend.js`) is a separate file that Amy manually pastes into her Apps Script project and redeploys — editing it in this repo does NOT update her live deployment. Any backend change must be called out explicitly as a manual step for Amy.

## [2026-09-10] - US-007
- Context: Amy reported "在总经理链接的'月度绩效奖金发放'里，Mia的（月度奖金）填好之后一刷新就又没有了" — filled-in monthly bonus data for Mia via the manager link disappears on page refresh.
- Root cause: `loadBestVisibleRecordForCurrentView()` (index.html ~4503, called from `autoLoadInitialVisibleRecord()` in `onMounted`, i.e. runs on every single page load) picks between the current local draft and any matching record in `visibleRecords` (local records library + whatever came down from cloud sync) purely by comparing `evaluationInputQuality()` — a hand-rolled "how filled-in is this" score where KPI dimension scores are weighted 1000x per KPI, but monthly-bonus fields are weighted only 10x per row. Anyone whose workflow is "just fill in the monthly bonus grade/amount" (exactly what the 总经理/manager persona does under "月度绩效奖金发放" — they are not expected to touch KPI scoring, that's Agnes's job) will almost always score far lower than ANY existing record for the same employee+period that has even one KPI scored — so on every reload, the manager's own just-typed draft gets silently discarded and replaced by whatever "looks more complete," with zero warning.
- Fix (two parts, both minimal):
  1. `hasQuarterProgress(data)` (index.html ~4688) now also treats a filled `grade`/`paid`/`comment` in any `monthlyBonuses` row as "real progress" (it previously only checked KPI dimensions, bonusItems, quarterlyOkrs, commissionPlan).
  2. `loadBestVisibleRecordForCurrentView()`: when the draft already matches the same employee+period as a candidate (`preferred` truthy) AND the draft has any `hasQuarterProgress`, return `null` immediately — skip the quality-score comparison entirely and just keep the draft. The quality-score fallback path is now reached only when there's no `preferred` match at all (i.e. genuinely bootstrapping a blank/unfamiliar session), which is the case it was actually meant for.
- Files changed: `index.html`.
- **Learnings for future iterations:**
  - To prove a fix like this actually fixes something (vs. just "looks right"), reproduce the bug against the PRE-fix code first: `git show HEAD:index.html > /tmp/old.html`, serve it alongside the current file from the same dev server (same origin ⇒ same localStorage), seed localStorage with a repro scenario, load the OLD file and confirm the bug fires, THEN load the current (fixed) file against the same seeded state and confirm it doesn't. Both this session's US-006 and US-007 fixes were verified this way — much more convincing than reasoning about the code alone.
  - `evaluationInputQuality()` (index.html ~3199) is the same "how complete is this record" heuristic used both here and in `submitCurrentToCloud`'s pre-submit guard (fixed in US-006) and in `shouldReplaceRecord` (still unfixed, see the note above about last-write-wins). It systematically underweights monthly-bonus-only workflows relative to KPI-scoring workflows. ## [2026-09-10] - US-008
- Context: after the SHARED_TOKEN migration above, Amy reported Mia's 2026-Q2 monthly bonus record appeared to be gone — every time she opened the manager link, "月度绩效奖金发放" showed unselected grades and 0 paid. Initially suspected this was fallout from switching to the new empty spreadsheet, but she confirmed it was the SAME computer/browser, and the record had genuinely been submitted via "保存并提交云端" before — and switching the period dropdown to 2026-Q2 (to go look for it) STILL showed blank, ruling out the "just viewing the wrong quarter" theory.
- Root cause: `rolloverDraftToPeriod(targetPeriod)` (index.html ~4792, invoked by the "季度" dropdown's `changeAssessmentPeriod` handler) unconditionally calls `applyProfileWithoutUndo(profile)` — which loads a BLANK profile template for the target quarter — whenever the target employee has a matching `PERSON_PROFILES` entry. It never checks whether `visibleRecords` already has a real saved record for that exact employee+period. So the act of switching the period dropdown itself was overwriting the currently-displayed (and about-to-be-autosaved) draft with a blank template, discarding whatever real record existed for that employee+period — completely independent of any cloud/spreadsheet issue.
- Fix: `rolloverDraftToPeriod` now looks up `visibleRecords.value.find(record => canonicalName(record.employeeName) === targetEmployee && record.period === targetPeriod)` BEFORE falling back to the blank-template path; if found, calls `loadRecord(existingRecord)` instead (mirrors the same lookup pattern already used in `loadBestVisibleRecordForCurrentView`/`quickOpenEmployee`).
- Files changed: `index.html`.
- **Learnings for future iterations:**
  - **Timing gotcha for testing this codebase**: `autoSave()` (index.html, watches most reactive form refs) debounces localStorage writes by 2000ms. When testing via browser automation, reading `localStorage.getItem('monthly_bonus_okr_draft_v3')` immediately (within ~300ms) after triggering a change will read STALE pre-change data even though the Vue reactive state and rendered DOM have already updated — this produced a confusing false negative partway through verifying this exact fix. Always wait 2.5s+ after a triggering action before asserting on localStorage state; or better, assert on the rendered DOM / a exposed reactive value directly when timing matters.
  - This is now the THIRD distinct place in this codebase found to silently discard real in-progress or saved data in favor of a "different" version without asking: (a) `submitCurrentToCloud`'s completeness guard (US-006, fixed → now asks via confirm()), (b) `loadBestVisibleRecordForCurrentView`'s auto-load-on-mount (US-007, fixed → now respects `hasQuarterProgress`), (c) `rolloverDraftToPeriod`'s period-switch (this story, fixed → now checks for an existing record first). If a future report sounds like "I filled something in and it later just wasn't there," check whether it's yet another variant of this same family of bug before assuming it's something else (e.g. a sync/network problem).
